Audit and fix exact-set-intersection blind spot in Azure action matching

Systemic follow-up to 5dc7ce9 (managed identity assign/action fix).
_role_grants_self_escalation, DANGEROUS_AZURE_ACTIONS, and
SELF_ESCALATION_ONLY_ACTIONS all used exact-set-intersection
(actions & CONSTANT_SET or a in CONSTANT_SET) to check whether a role's
granted actions cover a target capability. This misses any grant that
covers the target via Azure's mid-path wildcard convention (the same
shape as userAssignedIdentities/*/assign/action) rather than an exact
string match - e.g. a role granting "Microsoft.Authorization/
roleAssignments/*" would cover roleAssignments/write but never equal
any literal in DANGEROUS_AZURE_ACTIONS.

Introduced _action_covered(target, granted_actions) and
_any_action_covered(targets, granted_actions), both using
fnmatch.fnmatch with target as the "name" side and each granted action
as the "pattern" side - direction matters, since Azure grants (not
targets) are the side that legitimately contains wildcards. Applied
consistently to:
- _role_grants_self_escalation (was: actions & DANGEROUS_AZURE_ACTIONS)
- _role_definition_privilege's SELF_ESCALATION_ONLY_ACTIONS exclusion
  (was: actions - SELF_ESCALATION_ONLY_ACTIONS, a literal set diff)
- _grants_managed_identity_assign (unified with the same helper instead
  of its own inline fnmatch + "== *" check)

Also removed a stray, unused "from rich import scope" import shadowed
by local `scope` variables in two functions - harmless but confusing,
left over from an editor autocomplete.

Live-verified via full rescan: same 3 role_chaining alerts (138, 139,
140) and same node/edge counts (1129/163) as before the fix -
confirms no regression. No new alerts fired against the current live
Azure role set, meaning none of the 923 role definitions in this
subscription happen to grant a covered-but-not-literal dangerous
action today - the fix closes a real class of blind spot even though
this particular dataset didn't have a role that exercised it.
